Qwen3-TTS Base runtime research#

This port recovers the Qwen3-TTS Base 1.7B candidate evaluated in OpenRSI submission 6 and the Base 0.6B candidate evaluated in submission 10. The historical complete candidates improved non-streaming concurrency-16 throughput by 44.36% (0.6B) and 26.15% (1.7B); streaming throughput improved by 7.17% and 6.20%, respectively. These measurements use the historical source and are not a new benchmark of the current upstream port, or an isolated measurement of any one component. The older upstream comparisons below cover the exact-frame implementation. Their source revisions remain explicit. Separate Radix comparisons isolate the review-time bucketing candidate within the PR runtime. The final policy retains bucketing for 1.7B and exact-frame captures for 0.6B.

Runtime changes#

  • Base cloning requests use the existing full prefill graph backend, with token buckets through 1,024 for 1.7B and the 8,192-token prefill budget for 0.6B. CustomVoice retains its existing 512-token ladder; VoiceDesign and unknown variants keep the breakable default.

  • For 1.7B, whole-utterance CUDA vocoding uses 16-frame buckets through 256 frames and batch sizes 1–4: up to 64 graphs. Requests are zero-padded to the smallest captured frame bucket and decoded audio is trimmed to the original length. Unsupported shapes, deterministic decoding and disabled graphs use the original tokenizer path.

  • For 0.6B, whole-utterance CUDA vocoding preserves the native chunk/context boundaries (300/25 codec frames), uses exact lengths 1–325 for one or two requests (650 graphs), and uses a dedicated stream. Default non-streaming vocoder batching becomes two requests with no collection wait; explicit overrides win. Whole-utterance graphs require a recognized Base checkpoint size.

  • Capture larger shapes first within a shared graph pool to limit reserved memory fragmentation. This adds startup work and resident graph memory.

  • The initial incremental decoder launches its next cohort before resolving the previous one, retaining at most two in flight. Existing tail-decode routing, invalid-row handling and cancellation ownership remain in use.

  • Fence each codec arena host index slot’s outstanding upload before ring reuse. The four-slot ring and index values are unchanged.

Upstream already contains the historical invalid-row-mask transport mechanism in #2548. This port uses that implementation. It also preserves the follow-up scheduling in #2400 and the first-chunk tail runner in #2658.

Bucketed whole-utterance graphs#

The review-time change adopts db-ol’s bucketing implementation, retaining the original author attribution. For 1.7B it replaces up to 1,024 exact-frame captures with 64 graphs. The candidate also reduced 0.6B to 42 graphs, but the independent three-seed check below showed higher corpus WER in all three pairs. Commit 6075e99c902d1e9565110c20b5f155139dd7b4ad therefore restores the 650 exact-frame 0.6B captures and disables frame padding for that holder. This is a conservative default-policy decision; the serving measurements do not establish that padding caused the shift.

Capture remains in descending shape order within a shared pool. Only the 1.7B whole-utterance holder enables frame padding; initial and follow-up streaming graph policies are unchanged. The 0.6B native 300/25-frame chunk/context boundaries and reference-prefix trimming remain in place. Static inputs are cleared before every replay; returned audio is cloned and trimmed to the original frame count.

The tokenizer already zero-pads shorter requests to the longest request in a native batch. Batch composition can therefore change tensor shapes and floating-point results even without CUDA graphs. The causal decoder permits trailing padding, but bitwise equality with a narrower native call is not the contract for the bucketed path. The appropriate replay check compares the graph with eager execution at the same padded shape, then checks original-length trimming and fallback behavior.

The reviewer reported H200 SeedTTS EN non-streaming C16 results with interleaved seeds 42/43/44: mean startup decreased from 333 to 157 seconds for 1.7B and 317 to 150 seconds for 0.6B over four launches each, with mean latency and WER within their observed run-to-run variation. These are reviewer-reported results; they were not independently recomputed from raw records in this evidence archive and are not pooled with the measurements below.

Earlier native-padding diagnostic#

A native-decoder padding diagnostic on 2026-10-15 provides a direct check of that contract. It used the pinned 1.7B tokenizer below, BF16, the configured 29 fused SnakeBeta modules, H200, PyTorch 2.13.0+cu130, Transformers 5.12.1 and qwen-tts 0.1.1, without the optional flash-attn package. The tokenizer used its native PyTorch fallback. The 66 cases combined frame lengths 31/32/33/63/64/65/127/128/129/255/256, batch sizes 1/2/4 and fixture seeds 7/11. Each batch retained its native longest length; shorter rows used the native zero-code padding. The alternative padded that longest length to the next power of two. Both outputs were trimmed to each row’s original length and reference-prefix boundary.

All 66 identical-shape repeats and all 24 cases needing no extra padding were bitwise equal. Of the 42 cases with additional padding, 34 changed retained waveform samples. For example, a single 31-frame request padded to 32 frames had maximum absolute difference 0.0541992 and mean absolute difference 0.00139271 after trimming five reference frames. Differences were also present outside its last two frames. The largest absolute difference over the matrix was 0.223145.

These are synthetic valid codec IDs decoded by the real tokenizer, with eager execution on both sides. They demonstrate that padding and trimming do not preserve byte parity for this backend. They do not measure perceptual quality, serving performance or a CUDA-graph bucketing implementation. Result JSON SHA-256: d4e9d5da648c5e5ecfd4c6030845736a1c8f3c7fef88135060370dcb4635c557. The complete fixture matrix and executed script are retained in the evidence repository, which requires access.

The first counterexample can be reproduced from this checkout with MODEL_PATH pointing to the pinned 1.7B snapshot:

import os

os.environ["SGLANG_OMNI_TORCH_COMPILE_DEFAULT"] = "0"

import torch

from sglang_omni.models.qwen3_tts.stages import load_qwen3_tts_tokenizer
from sglang_omni.utils.snake_beta import fuse_vocoder_decoder

torch.set_num_threads(4)
torch.set_num_interop_threads(1)
tokenizer = load_qwen3_tts_tokenizer(
    os.environ["MODEL_PATH"],
    device="cuda:0",
    dtype="bfloat16",
    attn_implementation=None,
)
decoder = tokenizer.model.decoder.eval()
fuse_vocoder_decoder(decoder)
quantizers = tokenizer.model.config.decoder_config.num_quantizers
generator = torch.Generator().manual_seed(7 * 10000 + 31 * 10 + 1)
codes = torch.randint(0, 128, (1, quantizers, 31), generator=generator).cuda()
padded = torch.nn.functional.pad(codes, (0, 1))
with torch.inference_mode():
    decoder(torch.zeros_like(padded))
    native = decoder(codes).clone()
    repeat = decoder(codes).clone()
    bucketed = decoder(padded).clone()
    assert torch.equal(native.view(torch.uint8), repeat.view(torch.uint8))
    native = native[..., 5 * 1920 : 31 * 1920].float()
    bucketed = bucketed[..., 5 * 1920 : 31 * 1920].float()
    print((native - bucketed).abs().max().item())

The diagnostic above checks narrower versus padded eager execution; it does not establish that the numerical difference is larger than the native batch-composition effect, or that frame bucketing is unsuitable. The new replay tests compare padded graphs with padded eager execution for both Base sizes. Disabling the existing initial_cuda_graph option retains the tokenizer fallback and also disables initial streaming graphs.
